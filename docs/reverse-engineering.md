# 只用一块 ESP32 逆向：没有 Mac、没有安卓机

原仓库是这样抓包的：在 iPhone 上装 Apple 的 Bluetooth Logging Profile，导出 sysdiagnose，再去 HCI 日志里找
`LE_Set_Extended_Advertising_Data`。这条路要折腾描述文件和日志，而且每抓一次都要导一次。
安卓可以开 HCI snoop，但我们手边没有安卓机，也没有 Mac。

我们换了个方向：**不在手机这边抓，而是在空中收。** 失控 4.0 本来就是被动扫描广播的设备，
那就让一块 ESP32 跟它一样被动扫描，手机上的官方小程序发什么，板子就记下什么。
这块板子抄完帧也不用拆，接着当长期的远控广播器用。

## 需要什么

- 一块 ESP32-C3 开发板（或者任何支持 BLE 的 ESP32），刷这个仓库的固件
- 一台能跑 `shikong.server` 的电脑或服务器
- 一部能开官方小程序的手机（iPhone 就行）

## 抄帧流程

1. **先让那一路真的动起来。** 在小程序里打开，用手确认它在动，再开始扫。
   不确认就容易抄到 `0x57`，那是「档位设好但没开」的状态。我们第一次抄的整批帧都是这个，重放时设备一动不动，白解了一上午。
2. **只用被动扫描**：
   ```bash
   curl -H "$H" localhost:8765/api/toy/command -H 'content-type: application/json' \
        -d '{"action":"scan","ms":30000,"active":false}'
   ```
   **千万别用主动扫描。** 主动扫描会往外发 scan 请求、占住信道，手机发给玩具的控制帧会被盖掉
   （表现为拖滑块玩具不动），还可能把玩具弄进只能断电才恢复的状态。
3. 扫描的 30 秒里**一次只改一个东西**，比如只拖档位滑块，或者只切模式，好看出哪个字节跟着变。
4. 把结果存下来再解码：
   ```bash
   curl -H "$H" localhost:8765/api/toy/scan > scan.json
   python3 tools/decode_frames.py scan.json
   ```
   板子按 UUID 去重，每个不同的帧记一条，带首次和末次出现的时间（毫秒）和收到的次数（每次扫描最多 48 种帧）。
   `decode_frames.py` 按时间把帧排开，把和上一帧不一样的字节标黄，再检查校验、列出会话号：
   ```
       t0     t1   n  | 00 01 02 03 04 05 06 07 08 09 10 11 12 13 14 15 | 变化       会话号  掩码  校验
       16   5490 106 | 2d 02 00 15 3e 2d 00 01 44 52 00 52 3a 17 00 71 |            4452    52    ok
     5571   9149  74 | 29 02 00 15 2c 2d 00 01 44 52 00 52 48 17 00 71 | b0,b4,b12  4452    52    ok
   ```
   只变 byte 4 和校验、序号，说明 byte 4 就是入体档位。
5. **拿猜出来的帧去验证**，不用改代码，直接让板子广播原始帧（每帧播 `ms` 毫秒，播完自动发全停）：
   ```bash
   curl -H "$H" localhost:8765/api/toy/command -H 'content-type: application/json' \
        -d '{"action":"raw","frames":["2d0200153e2d0001445200523a170071"],"ms":3000}'
   ```
   入体的停止掩码、反着的档位、`0x07` 停不住，都是这样一帧一帧试出来的。

## 我们是怎么定下入体协议的

- 抄到的入体运行帧，跟吮吸帧比，byte 3/4/5 和 byte 11 不一样。byte 3 = `0x15`、byte 5 = `0x2D` 三次会话都没变，
  所以把它们当成固定值。
- 档位滑块往冲的方向拖，byte 4 反而**变小**，所以入体档位是反的。
- 停止：小程序关掉入体时发的是 `0x07`，但重放 `0x07` 停不住。改成 `0x02`（「停 + 入体位」）才停得住。
  再加上吮吸的 `0x01`，推出掩码的规律：高 4 位表示开停，低位表示通道，`0x03` 两路都停。
- 抄帧时为了解校验，我们自己推过一个公式：
  `byte12 = byte0 − (b1+…+b5+b11) + 0xE1`。后来原仓库给出了更干净的规则：
  **byte 0 = byte 1–15 之和**（byte 12 是序号）。会话号是 `44 52` 时两条规则完全等价，现在统一用原仓库的写法。
- **会话号**：同一台玩具，入体帧带 `44 52` 能动，吮吸帧带 `27 C6` 却没反应。被动扫一次就发现小程序两路都在用 `44 52`，
  把吮吸的会话号也换成它以后，两路都能用了。

## 踩过的坑（按浪费的时间排序）

1. **会话号**（见上）：两路一起不动时，第一件事是被动扫一次，看看 byte 8–9。
2. **固件尾巴最多 4 帧**，多出来的会被静默丢掉。入体停不下来就是因为它的停止帧被截掉了。
3. **主动扫描会盖掉手机的控制帧。**
4. **抄到的是 `0x57` 假状态**：抄帧时那一路必须真的在动。
5. **ack 超时要比板子空闲时的轮询间隔长**，不然空闲时发的指令有一半会报「没确认」，看起来就像「发了没反应」。
6. **从一路切到另一路时，要显式停掉旧那一路**：板子换表时不会跑旧表的尾巴，不停的话旧那一路会一直跑下去。
